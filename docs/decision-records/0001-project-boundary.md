# ADR 0001：项目边界和独立 fork 方向

- 状态：Accepted
- 日期：2026-08-31

## 背景

目标不是把 ROS 1 EGO-Planner 做成最小编译修改，而是抽离其飞行规划算法核心，重写为 ROS 2 兼容实现，并加入不确定性风险感知和动态障碍物轨迹预测。

## 决策

建立独立项目 `aurora-planner`，产品名为 AURORA-Planner。采用纯算法核心 + ROS 2 适配层的结构：

- 参考并重写 EGO 的概率地图、三维 A*、B-spline、轨迹优化、局部重规划和安全流程；
- 在核心层增加动态目标预测、时空碰撞和风险约束；
- 使用 ROS 2 标准工具、成熟传感器驱动、仿真器、飞控适配和可视化替换上游不属于飞行规划核心的模块；
- 上游 `ego-planner` 只作为只读参考，不在其目录内继续发展 AURORA。
- 首个复现阶段采用纯 C++ 核心、固定静态场景和数据回放；ROS 2 通信与仿真在算法基线通过后接入。
- 支持 Ubuntu 22.04 + ROS 2 Humble 和 Ubuntu 24.04 + ROS 2 Jazzy 两套组合，核心代码统一使用 C++17。

## 原因

这样可以让算法在没有 ROS 的情况下测试，减少 ROS 1/ROS 2 消息和生命周期耦合，同时保持 EGO 对三维飞行轨迹质量和实时性的关键约束。动态预测和风险感知也能拥有清晰的输入、时间和协方差契约。

## 后果

- 初期工作量大于逐文件迁移，需要先冻结上游行为基线。
- 需要自行维护消息、回放数据、指标、许可证和长期 API 兼容。
- 可以独立替换地图后端、求解器、预测器和飞控适配，但每次替换都必须通过统一契约和回归基准。

## 约束

上游仓库声明 GPLv3；直接复制或改写上游代码时必须保留相关版权和许可证，并在发布前完成法律/许可证审查。是否采用干净房间式重写，应在首次代码迁移前通过新的 ADR 定案。
