# ADR 0007: Emergency Stop Reset Boundary

- 日期：2026-09-01
- 状态：已确认并实现第一版
- 范围：`aurora_ros` 急停服务、规划线程和轨迹发布边界

## 决策

`SetEmergencyStop.engage=true` 进入锁存急停，禁止待处理规划继续执行；`engage=false` 只发起显式复位。复位后不能自动恢复旧任务，必须收到新的显式 `PlanningRequest`。

服务回调在互斥锁内清除 `pending_request_` 和动态自动重规划事件；复位同时清除 `latest_request_`、活动轨迹和已处理请求状态，并递增 `reset_generation_`。规划线程处理复位标志时再次清空相关槽位，以处理复位请求与 ROS 消息并发到达的情况。

每次规划工作携带开始时的复位代次。规划完成准备发布前，如果急停已锁存、复位仍待处理或代次已变化，就丢弃该计算结果，不更新活动轨迹，也不发布旧结果或可执行轨迹。

## 原因

仅设置一个原子急停标志不足以处理待处理请求和正在计算的结果：旧请求可能在 reset 后自动执行，正在运行的规划也可能在急停后发布新轨迹。清空请求槽位和代次失效机制把急停变成明确的执行边界。

## 后果

- 急停锁存期间到达的显式请求和动态目标只会被保存/诊断，不会执行；复位时全部丢弃。
- reset 后动态快照可以继续保存，但在新的显式规划请求到达前不会触发自动规划。
- 正在计算的请求被取消时，当前版本不发布该请求的 `PlanningResult`；调用方必须依赖急停状态和后续新请求重新建立规划闭环。
- 活动轨迹在复位后被清除，FSM 从初始等待状态重新开始，不继承旧任务进度。

## 验证

`test_emergency_stop_service_requires_new_request_after_reset` 使用真实 DDS 服务客户端验证：engage 返回 `accepted=true, active=true, latched=true`；锁存期间提交的请求 `request_id=201` 及随后动态心跳均不产生结果；reset 返回非活动状态且旧请求不在复位后执行；新的显式 `request_id=202` 请求成功生成三维轨迹。动态碰撞场景仍验证急停锁存和无轨迹发布。完整工作区回归为 100 个测试条目，0 errors、0 failures、0 skipped。
